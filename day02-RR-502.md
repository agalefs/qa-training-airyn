# Test Design: RR-502 Rental Lifecycle

## 1. State-Transition Table

| Current State \ Event | `pick-up` | `return` | `customer cancel` | `no-show timeout` (12:00 day after start date) |
| :--- | :--- | :--- | :--- | :--- |
| **Reserved** | **Active** *(Valid)* | **Rejected** *(Invalid: Cannot return before pick-up)* | **Cancelled** *(Valid)* | **Cancelled** *(Valid: Deposit forfeited)* |
| **Active** | **Rejected** *(Invalid: Item already picked up)* | **Returned** *(Valid)* | **Rejected** *(Invalid: Cancel after pick-up not allowed; must return)* | **Rejected** *(Invalid: Timeout only applies to Reserved state)* |
| **Returned** *(Final)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* |
| **Cancelled** *(Final)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* | **Rejected** *(Invalid: Final state)* |

## 2. Test Cases (Valid & Invalid Transitions)

### Valid Transitions (100% 0-Switch / Single Transition Coverage)

* **ID:** `TC-502-01` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Valid Transition: Reserved $\rightarrow$ Active (`pick-up`)
  * **Preconditions:** **User:** Counter Clerk (`clerk_01`). **Item:** `ITEM-201` (Assigned to rental, Status: `Reserved`). **Data:** Rental `RNT-1001` in `Reserved` state, Start Date `2026-11-17`. **Clock:** `2026-11-17 09:30`.
  * **Steps:** 1. Open rental `RNT-1001`. 2. Execute `pick-up` action as clerk hands item over.
  * **Expected Result:** Rental state changes from `Reserved` to `Active`. Pick-up timestamp is recorded as `2026-11-17 09:30`. Item status updates to `Rented`.

* **ID:** `TC-502-02` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Valid Transition: Active $\rightarrow$ Returned (`return`)
  * **Preconditions:** **User:** Counter Clerk (`clerk_01`). **Item:** `ITEM-201` (Status: `Rented`). **Data:** Rental `RNT-1002` in `Active` state. **Clock:** `2026-11-19 14:00`.
  * **Steps:** 1. Open rental `RNT-1002`. 2. Execute `return` action upon inspecting and receiving item back.
  * **Expected Result:** Rental state changes from `Active` to `Returned` (final state). Return timestamp is recorded. Item status updates to `Available`, and deposit release/settlement is triggered.

* **ID:** `TC-502-03` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Valid Transition: Reserved $\rightarrow$ Cancelled (`customer cancel`)
  * **Preconditions:** **User:** Counter Clerk (`clerk_01`) or Customer Portal User (`cust_55`). **Item:** `ITEM-202` (Status: `Reserved`). **Data:** Rental `RNT-1003` in `Reserved` state, Start Date `2026-11-18`, Deposit `$50.00` paid. **Clock:** `2026-11-17 16:00`.
  * **Steps:** 1. Open rental `RNT-1003`. 2. Trigger `customer cancel` event.
  * **Expected Result:** Rental state changes from `Reserved` to `Cancelled` (final state). Item `ITEM-202` is released back to `Available` pool. Deposit is refunded (not forfeited).

* **ID:** `TC-502-04` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Valid Transition: Reserved $\rightarrow$ Cancelled (`no-show timeout` at 12:00 day after start date)
  * **Preconditions:** **User:** System Scheduler (`sys_cron`). **Item:** `ITEM-203` (Status: `Reserved`). **Data:** Rental `RNT-1004` in `Reserved` state, Start Date `2026-11-16`, Deposit `$50.00` paid. **Clock:** `2026-11-17 12:00:01` (12:00 on the day after start date).
  * **Steps:** 1. Run scheduled timeout batch job / advance system clock past `2026-11-17 12:00`. 2. Query rental `RNT-1004`.
  * **Expected Result:** Rental state automatically transitions from `Reserved` to `Cancelled`. Deposit (`$50.00`) is marked as **forfeited**. Item `ITEM-203` is released to `Available`.

### Invalid Transitions (Negative State Testing)

* **ID:** `TC-502-05` | **Technique:** `ST` | **Priority:** `P2`
  * **Title:** Invalid Transition: Reserved $\rightarrow$ `return`
  * **Preconditions:** **User:** `clerk_01`. **Item:** `ITEM-204` (Status: `Reserved`). **Data:** Rental `RNT-1005` in `Reserved` state. **Clock:** `2026-11-17 10:00`.
  * **Steps:** 1. Open `RNT-1005`. 2. Attempt to trigger `return` action (via UI or API).
  * **Expected Result:** Action is rejected with error ("Cannot return a rental that has not been picked up"). State remains `Reserved`.

* **ID:** `TC-502-06` | **Technique:** `ST` | **Priority:** `P2`
  * **Title:** Invalid Transition: Active $\rightarrow$ `pick-up` (Duplicate pick-up)
  * **Preconditions:** **User:** `clerk_01`. **Item:** `ITEM-205` (Status: `Rented`). **Data:** Rental `RNT-1006` in `Active` state. **Clock:** `2026-11-17 11:00`.
  * **Steps:** 1. Open `RNT-1006`. 2. Attempt to trigger `pick-up` action again.
  * **Expected Result:** Action is rejected with error ("Rental is already active"). State remains `Active`; original pick-up timestamp is unchanged.

* **ID:** `TC-502-07` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Invalid Transition: Active $\rightarrow$ `customer cancel`
  * **Preconditions:** **User:** `clerk_01`. **Item:** `ITEM-206` (Status: `Rented`). **Data:** Rental `RNT-1007` in `Active` state. **Clock:** `2026-11-17 15:00`.
  * **Steps:** 1. Open `RNT-1007`. 2. Attempt to execute `customer cancel`.
  * **Expected Result:** Action is rejected with error ("Active rentals cannot be cancelled; item must be returned"). State remains `Active`.

* **ID:** `TC-502-08` | **Technique:** `ST` | **Priority:** `P1`
  * **Title:** Invalid Transition: Active $\rightarrow$ `no-show timeout` (Scheduler safety check)
  * **Preconditions:** **User:** `sys_cron`. **Item:** `ITEM-207` (Status: `Rented`). **Data:** Rental `RNT-1008` in `Active` state (picked up on `2026-11-16 14:00`), Start Date `2026-11-16`. **Clock:** `2026-11-17 12:05`.
  * **Steps:** 1. Run scheduled timeout batch job at `2026-11-17 12:05`. 2. Query rental `RNT-1008`.
  * **Expected Result:** Timeout job ignores `RNT-1008`. State remains `Active` and deposit is NOT forfeited.

* **ID:** `TC-502-09` | **Technique:** `ST` | **Priority:** `P2`
  * **Title:** Invalid Transitions from Final State: `Returned` $\rightarrow$ (`pick-up`, `return`, `customer cancel`, `no-show timeout`)
  * **Preconditions:** **User:** `clerk_01` / `sys_cron`. **Item:** `ITEM-208` (Status: `Available`). **Data:** Rental `RNT-1009` in `Returned` state, Start Date `2026-11-16`. **Clock:** `2026-11-17 12:05`.
  * **Steps:** 1. Attempt `pick-up` on `RNT-1009`. 2. Attempt `return` on `RNT-1009`. 3. Attempt `customer cancel` on `RNT-1009`. 4. Run `no-show timeout` job.
  * **Expected Result:** All four events are rejected/ignored with final-state error ("Rental is closed in Returned state"). State remains `Returned` throughout.

* **ID:** `TC-502-10` | **Technique:** `ST` | **Priority:** `P2`
  * **Title:** Invalid Transitions from Final State: `Cancelled` $\rightarrow$ (`pick-up`, `return`, `customer cancel`, `no-show timeout`)
  * **Preconditions:** **User:** `clerk_01` / `sys_cron`. **Item:** `ITEM-209` (Status: `Available`). **Data:** Rental `RNT-1010` in `Cancelled` state, Start Date `2026-11-16`. **Clock:** `2026-11-17 12:05`.
  * **Steps:** 1. Attempt `pick-up` on `RNT-1010`. 2. Attempt `return` on `RNT-1010`. 3. Attempt `customer cancel` on `RNT-1010`. 4. Run `no-show timeout` job.
  * **Expected Result:** All four events are rejected/ignored with final-state error ("Rental is closed in Cancelled state"). State remains `Cancelled` throughout.

## 3. Multi-Event Sequences (3+ Events / N-Switch Coverage)

Single-transition tests verify isolated edges, whereas multi-event sequences catch **race conditions, stale UI state, and side-effect leakage** (such as inventory locking or deposit status corruption) across state history.

### Sequence 1: `no-show timeout` $\rightarrow$ `pick-up` (late customer) $\rightarrow$ `return`
* **Why single transitions miss it:** Testing `Reserved -> Cancelled (timeout)` and `Cancelled -> pick-up (rejected)` separately won't catch a bug where a clerk leaves the rental screen open before 12:00, clicks `pick-up` at 12:02 (overwriting `Cancelled` via a stale UI state), and later tries to `return` the item—creating a rental with both a forfeited deposit *and* a completed return, or double-booked inventory.
* **Test Case (`TC-502-11` | `ST` | `P1`):**
  * **Preconditions:** **User:** `clerk_01` & `sys_cron`. **Item:** `ITEM-210` (Status: `Reserved`). **Data:** Rental `RNT-1011` in `Reserved` state, Start Date `2026-11-16`, Deposit `$50.00`. **Clock:** `2026-11-17 11:59`.
  * **Steps:**
    1. Clerk opens `RNT-1011` on screen at `11:59`.
    2. Clock advances to `12:01`; `no-show timeout` job runs in background (`Reserved -> Cancelled`, deposit forfeited).
    3. Clerk attempts `pick-up` on the already-open screen at `12:02`.
    4. Clerk attempts `return` on `RNT-1011` at `12:05`.
  * **Expected Result:** Step 3 is rejected due to optimistic lock / state mismatch (`Cancelled` is final). Step 4 is also rejected. `RNT-1011` remains `Cancelled` with deposit forfeited, and `ITEM-210` is never handed out without a valid new reservation.

### Sequence 2: `pick-up` $\rightarrow$ `customer cancel` (rejected) $\rightarrow$ `return` $\rightarrow$ `no-show timeout`
* **Why single transitions miss it:** An invalid `customer cancel` attempt while `Active` might partially execute a side effect before throwing an error (e.g., setting a `cancelled_flag = true` or queueing a deposit refund). When the customer subsequently performs a valid `return` and the 12:00 cron job runs later, that partial flag could cause a double refund or flip a `Returned` rental to `Cancelled`.
* **Test Case (`TC-502-12` | `ST` | `P1`):**
  * **Preconditions:** **User:** `clerk_01` & `sys_cron`. **Item:** `ITEM-211` (Status: `Reserved`). **Data:** Rental `RNT-1012` in `Reserved` state, Start Date `2026-11-17`, Deposit `$50.00`. **Clock:** `2026-11-17 09:00`.
  * **Steps:**
    1. Execute `pick-up` at `09:00` (`Reserved -> Active`).
    2. Attempt `customer cancel` at `10:00` (Rejected).
    3. Execute `return` at `11:00` (`Active -> Returned`).
    4. Advance clock to `2026-11-18 12:01` and run `no-show timeout` job.
  * **Expected Result:** Step 2 fails cleanly with zero database side effects. Step 3 transitions to `Returned` and triggers exactly one normal deposit refund. Step 4 ignores the `Returned` record, leaving final status as `Returned` and deposit status as `Refunded` (not `Forfeited`).
